# Local storage (message persistence)

Status: experimental, schema v1. Reference: `omcp-core::store`, `omcp-ffi::persist`.

Contacts, verification state, chats, messages, file-transfer metadata, received-file
references, the pending outbound queue, outgoing transfers and burn-after-read state
survive an app restart on Android and iOS. All of it lives in one encrypted SQLite file
per identity, written by the Rust core; the apps only hold the key.

## Encryption at rest

- SQLite is bundled (`rusqlite`, feature `bundled`); no SQLCipher/OpenSSL, so the same
  build works under cargo-ndk and for iOS.
- Each row is `nonce(24) ‖ XChaCha20-Poly1305(row_key, CBOR(record))` with
  `AAD = "OMCP-Store-v1" ‖ table ‖ 0x00 ‖ row id`. Rows can't be swapped or moved.
- Row ids and chat grouping columns are BLAKE3-keyed hashes of the natural ids. The
  file reveals row counts, sizes and insertion order, not peers, names, text or ids.
- `row_key` and `id_key` are BLAKE3 `derive_key` sub-keys of a 256-bit **storage key**
  generated by `generate_storage_key()` and held by the platform (PROTOCOL §3.2 item 4):
  - Android: sealed with the existing AES-256-GCM Android Keystore key (StrongBox when
    available) in app-private prefs. `allowBackup="false"`.
  - iOS: Keychain, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, not synchronizable.
    The DB is in Application Support, excluded from device backup,
    `completeUntilFirstUserAuthentication`.
- A sealed key-check row makes a wrong key fail cleanly (`FfiError::Storage`); the store
  is bound to one identity. The apps preserve a refused database and its journal,
  show a blocked-storage screen, and offer retry without replacing the store or key.

## Burn after read (PROTOCOL §19.1, REQUIREMENTS B1/B5)

- Burn content is stored only in the `burn` table, sealed under its own random
  per-message key (the `BurnStore` key); that key sits in a separate `burn_keys` row.
- Message rows for burn messages never hold content. An unsent burn message in the
  outbox is sealed under a sub-key of the per-message key.
- Burning deletes the key row, the content row and any unsent copy. `secure_delete = ON`
  zeroes freed pages and `journal_mode = DELETE` avoids WAL copies.
- Timers that ran out while the app was closed are applied on the next start, before
  anything is shown.
- Tests: `store::tests::b1_burned_message_is_not_recoverable_after_restart` (scans every
  file in the store directory for the plaintext, the per-message key and the ciphertext),
  `omcp-ffi` `burn_survives_restart_until_burned_then_is_unrecoverable`, and the Android
  and iOS bridge tests.

## Schema migrations

`PRAGMA user_version` tracks the schema. `MIGRATIONS[i]` takes a store from version `i`
to `i + 1` in one transaction. Never edit a shipped entry; append a new one. A store
written by a newer app is refused (`store schema is newer than this app`).

## Backup

Message history is backed up by the **chat backup** (v0.1.4, `chat_backup.rs`, see
[CHAT_BACKUP.md](CHAT_BACKUP.md)): a separate, incremental, padded backup keyed from
the 24 words. The Argon2id / platform-key identity backup (`backup.rs`) carries only
the identity, contacts with verification state and the profile name. Its optional
inner `history` field (written by pre-release builds of this store) is still **read**:
apps import it with `restore_history`, so those blobs keep restoring chats. New blobs
leave it out.

Store additions in v0.1.4 (no schema migration: new fields are optional CBOR keys
inside sealed rows, old rows decode with defaults):

- `FileRec.hash` (BLAKE3 content hash) and `FileRec.locator` (16-byte transfer id) so
  a restored placeholder can be re-requested; file states `Missing`, `Requested`,
  `Unavailable`.
- `ContactRec.device`: the contact's pinned identity signing key, current and
  superseded device keys, `restored_at` and the "Restored" badge expiry (RS1).
- `MessageRec.status = System` for the in-chat restore notice.
- Sealed `meta` rows `app:own_device` (this install's device key), `app:own_restored_at`,
  `app:chat_backup_state` and `app:media_backup_settings`.

Store additions in v0.1.4a (PeerID = BLAKE2b-256 of the identity key):

- `ContactRec.dh`: the contact's certified per-device X25519 key (absent = legacy
  contact keyed by its X25519).
- `app:own_device` also holds this install's X25519 seed (`dh_seed`); installs from
  earlier builds keep the seed-derived X25519 so contacts can still reach them.
- `Store::rebind_owner` moves the owner from the legacy X25519 id to the PeerID on first
  open; `Store::rekey_peer` re-keys a legacy contact's contact, chat, message, outbox,
  file and burn rows to its PeerID in one transaction, on the first verified handshake.
- Identity backups carry `dh` per contact; older backups restore legacy contacts.

Schema v2 (v0.1.4b, "Keep sent media"): table `kept_media` holds, per sent non-burn file,
a small sealed index row (`KeptMediaRec`: message id, peer, content hash, kept time, size;
grouped so eviction lists only these) and a separate sealed row with the bytes, both under
the same row key and AAD scheme as every other table. Limits (`app:kept_media_limits`,
default 90 days / 2 GB) are applied on insert, on start and when changed, oldest first.
Burn-after-read and view-once media are never written here. Kept copies are re-keyed with
the contact (v0.1.4a migration) and are not part of any backup.

## Known gaps

- Filesystem and flash remnants (deleted journal blocks, wear-levelling) are outside what
  SQLite can scrub. The per-message key is shredded, but an old copy of the wrapped key in
  a freed FS block could still be opened with the storage key. A key held only in memory
  (PROTOCOL §19.1 item 4's first option) would mean burn messages don't survive a
  restart.
- Incoming partial transfers aren't persisted. After a restart the sender replays the
  whole file on the next link (existing resume behaviour).
- The per-chat burn default and notification settings stay in platform prefs, not in
  the store.
- No storage passphrase (PROTOCOL §4 "optional passphrase") and no remote wipe.
- iOS uses the Keychain, not the Secure Enclave, for the storage key (the Enclave only
  holds P-256 keys; wrapping through it is a possible follow-up).

### Fail-closed store opening

Opening an existing store now authenticates its storage key before migrations or
journal-mode changes. The native FFI entry point also checks the stored owner
against the requested current/legacy identity before these changes. A newer
schema, missing key-check in a versioned database, or nonempty unversioned
database is refused, not silently initialized. A genuinely new store creates
its schema and key-check in one transaction. Authenticated legacy owner rebinding
remains supported.

A refusal does not authorize deleting the database or its journal. SQLite may
itself recover a hot journal while opening or reading a file; this change is not
a guarantee that an operating-system-level read leaves every byte untouched.
These checks preserve the existing row encryption and OMCP wire protocol.
